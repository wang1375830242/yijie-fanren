# 设计宣言与不做清单

## 八行字

```text
做一个随机降生的修仙人生模拟。
玩家不能选择具体出身，只能活完一世。
没有排名，没有最优解，只有选择和后果。
境界、寿命、灵根、因果按同一套规则运转。
每一世结束时，留下这个人的纹理，而不是分数。
不是每一天都要登录的任务，而是一次可以回看的经历。
世界很宽，活法很多，不把任何一种人生放在另一种之上。
方法可以过时，态度和判断要留下。
```

## 做

- 让随机性决定起点，让选择决定过程。
- 让境界、寿元、关系、因果互相牵动。
- 让每一次重大选择留下可回看的一句话。
- 让同辈、故人、碑林成为世界的参照，而不是排行榜。
- 让死亡和失败也有尊严，不把人生写成单一的胜利。
- 新内容优先增加故事深度，而不是增加按钮数量。
- 数值改动必须能指出代码位置和可调边界。
- 玩家可感知的改动更新 changelog；设计理由留在本文件。

## 不做

- 不做每日任务、每周任务、签到式留存。
- 不做社交排行榜、战力榜、人生高低排名。
- 不给同辈或人生挂“金框”“稀有度”来暗示谁更成功。
- 不用“最高境界”作为唯一的人生评价。
- 不为了爽感随意破坏境界、寿元、因果规则。
- 不写没有依据的概率、没有来源的统计。
- 不把沉重的人生当成猎奇选项；需要时提供求助信息。
- 不因为一个建议就无限加按钮、加页面、加系统。
- 不把核心推演、结局、图表或本地存档完全绑在后端服务器上；没有服务器时，网页仍要能离线游玩。

## 判断一个新功能

依次问：

1. 它让玩家更接近“一个具体的人”，还是更接近“一个分数”？
2. 它是否会让某一种人生显得高于另一种？
3. 它是否让第一次进入的人更沉重、更迷失？
4. 它能否用现有数据表达，而不是新增一套平行系统？
5. 它是否值得进入 changelog，还是只属于内部实现？

只要第 1 或第 2 条答错，先不改。
